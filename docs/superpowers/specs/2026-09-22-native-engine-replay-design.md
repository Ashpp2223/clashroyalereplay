# 原生战斗引擎复盘器设计

日期：2026-09-22  
状态：待用户书面审阅  
目标版本：项目文件格式 v2

## 1. 背景与目标

现有应用以人工记谱、手工扣费和 CSS 棋盘模拟战斗。新版本把中央模拟区替换成真实 Android 游戏客户端渲染的战斗，并由 `Jason-XII/clash-royale-battle-engine` 驱动确定性对局。节点仍然存在，但含义变为某条时间线上的检查点：父节点到子节点按战斗时间推进，同一父节点的多个子节点代表从同一历史状态产生的平行分支。

第一阶段的目标是跑通标准卡组端到端闭环：启动引擎和模拟器、展示原生战斗画面、操作双方出牌、暂停/播放/变速/步进、创建节点、恢复节点并产生新分支、保存与载入 v2 项目。之后再扩展自定义卡组，以及觉醒、英雄/精英能力等机制。

## 2. 用户体验原则

- 中央区域显示游戏客户端的原生战斗画面，不重画竞技场、单位、卡牌或圣水条。
- 延用游戏战斗时的卡牌选择和圣水 HUD。界面用同一条原生视频流裁切并重新排布：敌方 HUD 在上、竞技场在中、我方 HUD 在下。
- 双方圣水始终可见，并与引擎状态一致；觉醒、卡牌等级、英雄/精英能力等视觉状态由游戏自身渲染。
- 用户可手动控制双方。点击任一方手牌和战场位置时，桌面应用把坐标映射回原生 1080×1920 画面并注入原生触摸。
- 创建节点是显式操作：先在精确 tick 暂停，再提交节点；创建后保持暂停。
- 切换到历史节点后第一次产生有效操作时，自动新建分支，保留原有所有子分支，绝不覆盖历史。
- 播放体验接近游戏自带回放：播放/暂停、0.25×/0.5×/1×/2×/4×、前进一步、后退一步和按时间跳转。

## 3. 范围与非目标

### 本期范围

- 本机 Tauri/React 应用、Python 引擎桥、Android Emulator 和原生游戏客户端的完整协作。
- 双方出牌与费用显示、原生 HUD、确定性时间线、分支、节点备注和布局。
- 新项目格式 v2、崩溃恢复日志、严格版本校验、自动启动和故障诊断。
- 标准卡组的真实模拟；随后以能力探测和白名单方式开放自定义卡组、觉醒与英雄/精英能力。

### 非目标

- 不导入官方对局回放日志。
- 不兼容或迁移旧 `.cr-replay.json` v1 文件；载入时明确提示格式不受支持。
- 不从 APK 中提取、复制或重写游戏 UI 类；只显示当前获许可运行时实际渲染的像素。
- 不将 Android 游戏画面替换成浏览器 CSS/Canvas 仿制品。
- 不在首期提供联网对战、云同步或多人协作。
- 不允许重接父子关系或把节点移动到另一个父节点，因为这会改变历史语义；允许删除整个子树。

## 5. 总体架构

系统分为四层：

1. **Tauri/React 前端**：节点树、备注、项目管理、播放控制、原生画面裁切视口、触摸坐标映射和状态提示。
2. **Tauri 主进程**：管理 sidecar 生命周期、项目文件和恢复日志；生成本次会话令牌；只允许 loopback 通信。
3. **Python 引擎桥**：封装上游 `RenderedEngine` 和探针协议，提供版本化本地 API；统一控制 tick、动作、快照、观测和错误。
4. **Android Emulator + 原生客户端/探针**：运行真实游戏渲染、处理卡牌/圣水/觉醒/能力 UI，并通过 Emulator gRPC/WebRTC 输出视频和接受触摸。

前端不得直接依赖上游 TCP 行协议或 ADB 命令。所有引擎细节收敛在桥接层，便于未来把 Python 冻结成 Tauri sidecar，并在不改 UI 数据模型的情况下升级引擎。

## 6. 运行时启动与生命周期

启动状态机为：

`未启动 → 环境检查 → 启动模拟器 → 等待 ADB → 校验运行时 → 注入/启动探针 → 启动战斗 → 建立 WebRTC → 就绪`

具体要求：

- 自动发现 Android SDK；首选固定 AVD `CR_Null_ARM64_API30`，也允许配置等价的 Android 30 ARM64 AVD。
- 等待设备上线、boot completed、root/探针权限和目标包可用，每一步有独立超时与可操作错误信息。
- 在任何编辑会话开始前校验上游提交、探针、APK、`libg`、内容版本和运行时指纹。任一不匹配均进入只读诊断态，禁止创建或修改战斗历史。
- 引擎以固定随机种子和匹配配置重置；桥接层确认首个稳定观测后，才把 UI 标记为“可操作”。
- WebRTC 断开、探针失联或观测 tick 不连续时立即暂停。重连成功后恢复到最后一个已提交节点，不猜测丢失区间。
- 正常退出依次暂停、刷写日志、释放原生快照、关闭连接；只终止本应用启动的子进程，不影响用户其他模拟器实例。

## 7. 原生画面与 HUD 布局

探针的基准原生画面为 1080×1920，并提供以下已知布局：竞技场 `(54,282)-(1026,1666)`，世界可落点 `(111,436)-(967,1666)`，敌方手牌中心 y=`171`，我方手牌中心 y=`1749`，四个槽位中心 x=`211/354/497/640`，卡牌半宽/半高为 `67/86`。敌方顶栏的槽位视觉顺序与 owner 0 的逻辑顺序相反。

这些数值作为固定运行时的内置裁切配置，而不是散落在组件中的常量。桥接层在握手时返回：

- 原生帧尺寸与旋转方向；
- 竞技场、双方 HUD、有效落点区域矩形；
- 双方手牌槽位映射、镜像/反序规则；
- 当前配置 ID 与探针版本。

前端以一个隐藏的完整 WebRTC 视频元素为唯一像素源，通过多个裁切视口显示：

- 顶部：敌方原生手牌与圣水 HUD；
- 中部：原生竞技场；
- 底部：我方原生手牌与圣水 HUD。

视口使用 `object-fit` 等比缩放和显式裁切矩阵，不对画面做非等比拉伸。窗口缩放、DPI 和留黑都必须纳入逆变换。点击手牌或竞技场时，前端先由视口坐标逆变换到原生像素，再发送给桥接层；桥接层进行边界校验后注入触摸。调试模式可显示裁切框、映射后的原生坐标和最后一次触摸点，但发行模式默认关闭。

双方圣水的视觉显示以原生 HUD 为准；结构化观测中的双方 elixir 仅用于一致性校验、时间线摘要和无障碍文本，不覆盖或伪装原生 HUD。

## 8. 输入、动作确认与特殊机制

桌面应用发送的是输入意图，不直接写历史。一个出牌动作只有在探针返回已接受结果，并且后续结构化观测确认对应 tick、手牌/费用或实体变化后，才进入事件日志。费用不足、非法落点、卡牌不可用或能力冷却等拒绝操作不会污染历史。

统一动作模型至少支持：

- `play-card`：玩家、原生卡牌 ID、逻辑槽位、原生落点、目标 tick；
- `activate-ability`：玩家、原生实体/能力 ID、目标 tick；
- 后续由能力协商开放的其他确定性动作。

觉醒、等级、英雄/精英能力和冷却状态不由前端推算。桥接层读取探针的 rich observation 和 capability flags，并把支持状态暴露给项目配置页。未被当前引擎、运行时和探针共同确认的卡牌或机制，在开局前阻止选择；运行中若能力状态无法确认则暂停并报错。

首期标准卡组只开放已验证的 `play-card` 路径。自定义卡组阶段增加卡牌目录与能力矩阵，完成普通卡、觉醒卡及英雄/精英能力的逐项回归后才移出白名单。

## 9. 时间、播放与确定性

引擎逻辑时钟以 tick 为唯一权威，当前基线为 20 Hz。界面时间只由 tick 换算，不以浏览器 wall clock 作为历史依据。

- 播放：桥接层按选择的速度推进引擎；UI 消费确认观测。
- 暂停：在已确认 tick 边界停下。
- 前进一步：推进一个引擎 tick。
- 后退一步/任意 seek：恢复最近可用快照并确定性重放到目标 tick；没有快照时从根重放。
- 变速：只使用引擎支持的 `0.25/0.5/1/2/4`，速度变化本身不是战斗动作。
- 创建节点：先请求暂停并获取确认 tick，再将该 tick 和当前未提交动作段原子提交为新节点。

每次重放都校验动作结果和关键状态摘要。任何首个分歧都会停止恢复，并报告节点、动作序号、期望 tick 与实际观测，禁止静默继续。

## 10. v2 项目与事件模型

项目文件以语义化 schema 标识，例如：

```ts
interface ReplayProjectV2 {
  schema: "cr-native-replay.v2";
  projectId: string;
  title: string;
  createdAt: string;
  updatedAt: string;
  engine: EngineIdentity;
  match: MatchConfig;
  rootNodeId: string;
  nodes: Record<string, TimelineNode>;
  layout: TreeLayout;
}

interface EngineIdentity {
  upstreamCommit: string;
  probeSha256: string;
  apkSha256: string;
  libgSha256: string;
  runtimeFingerprintSha256: string;
  protocolVersion: string;
  cropProfileId: string;
}

interface TimelineNode {
  id: string;
  parentId: string | null;
  childIds: string[];
  finalTick: number;
  title: string;
  note: string;
  actionsFromParent: BattleAction[];
  stateDigest: StateDigest;
  createdAt: string;
}

interface BattleAction {
  id: string;
  tick: number;
  sequence: number;
  owner: 0 | 1;
  kind: "play-card" | "activate-ability";
  nativeCardId?: number;
  slot?: number;
  nativeX?: number;
  nativeY?: number;
  nativeEntityId?: number;
  nativeAbilityId?: number;
}
```

约束如下：

- 每条父子边的 `actionsFromParent` 按 `(tick, sequence)` 严格有序，tick 必须大于等于父节点 `finalTick` 且不大于子节点 `finalTick`。
- 节点的战斗历史一旦提交即不可变；标题、备注和纯视觉树布局可编辑。
- `stateDigest` 是校验与列表摘要，不是可恢复的完整状态，也不是事实来源。
- 原生 snapshot handle 只存在于当前进程内的 LRU 会话缓存，用于加速切换；不序列化到项目文件。进程重启后总能从种子、配置和动作重放恢复。
- 根节点包含已确认的初始 tick；项目持有固定种子、双方卡组和匹配配置。

## 11. 分支与节点操作

当前工作区维护 `checkedOutNodeId`、`workingTick` 和未提交动作段：

1. 选择节点时，暂停并恢复到该节点 `finalTick`，清空旧工作区。
2. 从节点继续播放但尚未有有效动作时，不创建空分支。
3. 第一个被确认的有效动作到来时，自动开启一条可见的草稿分支并进入“待提交新分支”状态；它不是已提交节点，原节点及已有子节点保持不变。
4. 用户点击“创建节点”时，把草稿分支中从所选节点至当前确认 tick 的动作段提交为新的子节点，并继续停在新节点。
5. 若用户切换节点且工作区有未提交动作，先自动写入恢复日志，再要求用户选择提交新节点或丢弃工作区；不得覆盖现有分支。
6. 删除节点等于删除该节点及所有后代，需明确列出影响数量并确认；根节点不可删除。

树边可显示父子之间的时间差、动作数和最终 tick，以强化“时间线/平行世界”语义。

## 12. 保存、恢复与崩溃日志

- 项目保存采用临时文件写入、校验、原子替换，避免半写文件。
- 文件载入后先做 schema、引用完整性、无环性、tick 单调性、动作排序、坐标边界和引擎身份校验，再允许启动战斗。
- v1 文件只显示“旧格式不受支持”，不做猜测性迁移。
- 未提交动作使用独立的 write-ahead journal，至少记录项目 ID、基节点、引擎身份、确认动作和最后确认 tick；每个动作确认后立即刷写。
- 启动时若发现匹配的日志，用户可恢复成待提交分支或丢弃。身份哈希不一致时仅允许导出诊断信息，不允许重放或编辑。
- 正常提交节点或显式丢弃后清理对应日志。

## 13. 本地 API 与安全

Python 桥仅监听 `127.0.0.1` 的随机空闲端口。Tauri 每次启动生成高熵会话令牌，经标准输入或受限启动参数传递；HTTP/WebSocket/WebRTC 信令请求均需令牌。接口按版本命名，并至少覆盖：

- runtime status / capabilities / crop profile；
- start/reset/pause/resume/speed/step/seek；
- submit native touch / structured action；
- observations and confirmed actions；
- snapshot create/restore/release；
- WebRTC offer/answer/ICE signaling；
- shutdown and diagnostic bundle。

跨域仅允许 Tauri 本地 origin，不监听局域网地址，不把令牌写入项目文件或普通日志。诊断包默认脱敏路径、令牌和受限资源信息。

## 14. 故障处理与可观察性

UI 使用清晰的状态页代替无限转圈，并为每个失败阶段给出“重试”“打开诊断”“返回只读项目”等动作。重点错误包括：SDK/AVD 缺失、ABI 错误、启动超时、ADB/root 不可用、版本或哈希不符、探针注入失败、WebRTC 失败、动作被拒绝、tick 分歧和快照失效。

日志按会话记录组件、时间、tick、请求 ID 和错误码，不记录会话令牌。开发模式可打开协议跟踪和原生坐标叠层；发行模式保留有限滚动日志。用户可一键生成包含版本、哈希、AVD 配置、最近状态转换和脱敏日志的诊断包。

## 15. 分阶段交付

### 阶段 A：固定基线与桥接骨架

Vendor 固定上游，建立版本清单、Python 桥、Tauri sidecar 管理和环境检查；用标准卡组启动确定性引擎。

### 阶段 B：原生画面与双方操作

接通 Emulator WebRTC，完成三个原生裁切视口、DPI/窗口坐标映射、双方手牌选择、竞技场落点和双方原生圣水显示。

### 阶段 C：时间线与项目 v2

实现播放控制、确认动作日志、节点创建、历史恢复、自动分支、snapshot 会话缓存、保存/载入和崩溃恢复。

### 阶段 D：自定义卡组与特殊机制

实现能力协商、卡牌支持矩阵、自定义卡组校验、觉醒和英雄/精英能力操作；不支持的内容继续在开局前阻止。

### 阶段 E：分发加固

冻结 Python 桥为 sidecar，补全受许可依赖的安装/打包路径、诊断工具、端到端稳定性和升级文档。

## 16. 测试策略

- **纯逻辑单测**：树不变量、自动分支、动作排序、tick 换算、v2 校验、日志恢复、裁切/逆坐标变换和敌方槽位反序。
- **桥接契约测试**：用录制协议样本验证状态机、拒绝动作、断线、哈希不符、snapshot 生命周期和重放分歧。
- **组件测试**：播放控制、启动/错误状态、三视口布局、节点删除确认、旧格式提示。
- **真实模拟器集成测试**：使用固定 ARM64 AVD 和标准卡组，验证启动、双方出牌、费用变化、视频重连、暂停/步进/变速、创建节点、跨分支恢复。
- **机制回归**：每个将开放的觉醒/英雄/精英能力至少包含一次成功操作、一次非法操作、一次保存后冷启动重放。
- **长稳测试**：连续运行、频繁 seek、创建大量分支和模拟 WebRTC/bridge 崩溃，确认无历史覆盖、无 snapshot 泄漏且可从 journal 恢复。

## 17. 验收标准

阶段 C 完成时必须同时满足：

1. 从桌面应用可自动启动受支持的模拟器和引擎，并在中央窗口看到真实游戏原生渲染。
2. 敌方原生卡牌/圣水 HUD 位于顶部，我方原生卡牌/圣水 HUD 位于底部，竞技场居中；缩放后点击仍准确。
3. 用户能控制双方出牌，只有引擎确认的操作进入历史；双方费用显示与原生状态一致。
4. 播放、暂停、五档速度、前进一步、后退一步和 seek 可用。
5. 创建节点停在精确 tick；从历史节点出牌自动形成新分支，原有子分支和后代完全保留。
6. 在同一会话中可借助 snapshot 快速切换；清空快照或重启应用后仍可由确定性重放得到相同 digest。
7. v2 项目可保存、关闭、重开并恢复所有分支、备注和布局；v1 文件不会被误读。
8. WebRTC 或桥接异常会自动暂停并恢复到最后提交节点；未提交动作可通过 journal 找回。
9. 任一版本或哈希不匹配会阻止编辑，不会在未知运行时上继续生成历史。
10. 标准卡组端到端测试稳定通过；觉醒/英雄/精英能力只有在各自回归通过后才可在自定义卡组中选择。

## 18. 已确定的取舍

- 选择“原生视频像素裁切 + 坐标回映射”，而不是移植游戏内部 UI 代码；这样保留游戏真实外观和机制状态，又避免与私有 UI 类强耦合。
- 选择“动作日志为持久事实、snapshot 为会话缓存”，兼顾可审计、可迁移和快速切换。
- 选择严格固定版本并阻止不匹配编辑，而不是尝试兼容未知运行时；确定性历史比宽松启动更重要。
- 第一阶段先证明标准卡组全链路，再开放自定义卡组；避免 UI 看似支持但引擎无法可靠重放的卡牌或能力。

## 19. 实施前仍需遵循的门槛

本文档获确认后，再编写逐文件、逐测试的实施计划。实施计划必须把阶段 A–C 拆成可独立验证的小步，并把阶段 D 保留为后续里程碑；在计划获确认前不修改产品代码。
